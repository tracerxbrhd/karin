# Обращение владельца Karin в Яндекс

Подготовлено 22.11.2026; **не отправлено**. Отправляет владелец своей
OAuth-регистрации через официальный канал, не Codex, CI или GitHub.

Подтверждённый канал: [«Форма обратной связи» в документации Яндекс ID](https://yandex.ru/dev/id/doc/ru/feedback).
Страница отвечает HTTP 200 и встраивает форму Яндекса
`https://forms.yandex.ru/surveys/1792/?iframe=1`. Она предлагает задать вопрос,
если ответ не найден в документации. Это канал обращения разработчика, а не
обещание одобрения Music-интеграции; в тексте ниже запрошена маршрутизация.
Старая ссылка обратной связи из §6.4 лицензии программы Яндекс Музыка при
проверке перенаправляла на общую Справку; отдельный адрес партнёрской команды
не предполагается. В обращение не нужно добавлять Client ID, Client secret,
токены, cookies, сведения аккаунта, JSON или приватные скриншоты.

## Текст для отправки

**Тема: Karin — условия независимой Linux-интеграции с Яндекс Музыкой и Music API**

Здравствуйте!

Я разрабатываю независимый открытый Linux-клиент Karin:
https://github.com/tracerxbrhd/karin. Прошу передать обращение командам
Яндекс ID/OAuth и Яндекс Музыки, уполномоченным разъяснить доступ к Music API,
использование OAuth-регистрации и условия распространения клиента.

Karin — приложение на Rust с GTK4/Libadwaita, GStreamer и D-Bus/MPRIS.
Целевая среда — Fedora KDE/Wayland; планируются Native- и Flatpak-сборки.
Собственный код и адаптированные GPL-компоненты распространяются по
GPL-3.0-or-later с сохранением лицензий и атрибуции. Это не официальное
приложение Яндекса. Публичный релиз интеграции ещё не объявлен; частный
прототип прошёл локальную функциональную проверку владельцем проекта.

Нужны следующие категории Music API: проверка доступного аккаунта; поиск и
каталог треков, альбомов, исполнителей; личная библиотека и чтение/изменение
своих плейлистов; Like/Unlike и Dislike; персональная «Моя волна» с её
предусмотренной обратной связью; онлайн-воспроизведение доступных пользователю
нешифрованных потоков; отображение обложек и разрешённых текстов песен.
DRM, платёжные, региональные или иные ограничения обходить не планируется.

26.10.2026 мной зарегистрировано собственное приложение Karin типа «Для
авторизации пользователей» с правами `music:api-public`,
`music:major-public-api`, `login:info`, `login:avatar`. При локальной
диагностике Authorization Code + PKCE S256 без Client secret обмен кода
завершился HTTP 200; `login.yandex.ru/info` подтвердил пользователя и
соответствие токена клиенту Karin. Однако `api.music.yandex.net/account/status`
и независимо `/account/about` вернули HTTP 403 с общей категорией отказа.
Включение/выключение TUN этого не изменило. Конкретная причина не установлена;
мы не считаем её доказательством недостаточной подписки, региона или scopes.
Повторять эти эксперименты либо менять идентичность ради обхода отказа не нужно.

Работающий обычный вход прототипа использует другой опубликованный механизм,
адаптированный из Cassette v0.2.4: опубликованную там общую регистрацию,
implicit-запрос с проверкой `state`, отдельную эфемерную WebKitGTK-сессию и
обмен её cookies через `sessionid` на официальном OAuth endpoint, затем
обязательную проверку Music-аккаунта. Поля `client_id` и `client_secret`
из опубликованной конфигурации включены в исходник и бинарник; это не собственная
регистрация Karin, и её фактический держатель не установлен одной атрибуцией
исходников. Она не представляется пользователю как собственная регистрация.
Заголовок идентичности Android-клиента не используется. Пароли/DOM не читаются,
JavaScript не внедряется, чужие профили браузеров и cookies не импортируются.
Только проверенный токен может сохраняться через защищённое хранилище;
недоступность хранилища допускает лишь сеанс в памяти. Работающий частный
прототип не рассматриваем как разрешение на использование регистрации или
публичное распространение интеграции.

Прошу разъяснить применимое основание и условия по следующим вопросам:

1. Предназначены ли `music:api-public` и `music:major-public-api` для независимых
   пользовательских музыкальных клиентов? Какие из перечисленных категорий и
   endpoints разрешены и какие дополнительные права нужны?
2. Какие дополнительные проверки, согласование, договор, верификация или
   allowlisting нужны собственной регистрации Karin? Как официально выяснить
   причину описанного Music 403 после успешной выдачи токена и проверки ID?
3. Какие OAuth-механизмы поддерживаются для независимого Linux-клиента?
   Допустим ли публичный native-клиент с Authorization Code + PKCE S256 без
   встроенного Client secret, и какие зарегистрированные callback URI и браузер
   следует использовать? Какие условия обновления/отзыва токенов обязательны?
4. Допустимы ли embedded WebKitGTK и описанный `sessionid`-механизм для Linux,
   либо требуется системный браузер или иной документированный SDK/flow?
5. Допускается ли Karin повторно использовать опубликованную регистрацию из
   Cassette? Кто вправе дать такое разрешение и требуется ли согласие её
   фактического держателя наряду с Яндексом? Просим пояснить применение §4.4
   условий API Яндекс ID к этой общей регистрации. GPL исходников не считаем
   разрешением на OAuth-регистрацию.
6. Допустимо ли публичное распространение независимых Native/Flatpak-сборок с
   разрешённой Music-интеграцией, в том числе через Flathub? Какие условия,
   атрибуция, уведомления, географические и пользовательские ограничения нужны?
7. Какие условия распространяются на каталог, персональные данные библиотеки,
   онлайн-воспроизведение, обложки и тексты? Какие права/ограничения должны
   проверяться и отображаться пользователю независимо от подписки и HTTP 200?
8. Допускается ли приватный ограниченный HTTP-аудиокеш для ускорения повторного
   воспроизведения с текущей авторизацией, HTTP freshness/revalidation и запретом
   хранения при `no-store`? Экспорт, распространение музыки и автономный доступ
   в обход актуального разрешения не предусматриваются; подписанные URL и
   credentials не сохраняются в кеше. Какие дополнительные пределы, срок
   хранения, очистка и ограничения контента обязательны?
9. Какие требования есть к названию сервиса, товарным знакам и явному обозначению
   независимости Karin от Яндекса? Официальные логотипы как собственный бренд
   использовать не планируется.

Просим указать применимые официальные условия или процедуру получения разрешения
и его границы отдельно для регистрации, API, контента и публичного распространения.
Если текущий механизм не допускается, просим описать разрешённый путь для
собственного приложения Karin. Техническая работа не должна подменять такое
решение или обходить отказ. Идентифицировать собственную регистрацию можно через
мой авторизованный кабинет; секреты и пользовательские credentials не направляю.

Спасибо!
Владелец проекта Karin и его собственной OAuth-регистрации

## Основание и следующий шаг

Проверены официальные документы на 22.11.2026:

- [Регистрация приложения](https://yandex.ru/dev/id/doc/ru/register-client) и
  [регистрация для авторизации](https://yandex.ru/dev/id/doc/ru/register-auth).
- [API Яндекс ID](https://yandex.com/legal/authid_api/en/), публикация 21.08.2026:
  §2.5.1–2.5.2 отделяют допуск к другим API; §4.4 требует уточнения прав на
  передачу/предоставление API Key.
- [Условия Музыки](https://yandex.ru/legal/music_termsofuse/ru/), русская редакция
  для России/Беларуси, публикация/вступление 25.08.2025: §2.1, §2.7–2.8.
- [Лицензия программы Яндекс Музыка](https://yandex.ru/legal/music_mobile_agreement/ru/),
  русская редакция для России/Беларуси, публикация/вступление 03.04.2026:
  §1.1 относится к программе Яндекса, §2.2 — к правам на материалы; она не
  выдаётся за разрешение Karin.

После ответа владелец фиксирует только безопасную сводку применимого основания,
условий и согласованного объёма, затем выполняется необходимая локальная
проверка. Приватная переписка не публикуется автоматически. До этого
[Issue #5](https://github.com/tracerxbrhd/karin/issues/5) остаётся открытой, а
публичный релиз интеграции в [#22](https://github.com/tracerxbrhd/karin/issues/22)
не объявляется. Подготовка кода, пакетов, исходников и проверок продолжается.
