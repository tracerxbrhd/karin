# Karin v0.4 — Cassette-like refinement task

Current owner task, starting at `a70bbf714e3d7ea775c03839eb01f0b1d9dd4f62`.
It supersedes conflicting older v0.4 instructions; historical verification remains
in [IMPLEMENTATION_REVIEW.md](IMPLEMENTATION_REVIEW.md).
Current implementation evidence, its exact source and remaining cold/Fedora
acceptance limits are recorded there separately from this unchanged owner task.

Продолжи работу над Karin в существующем Draft PR #15.

Репозиторий: tracerxbrhd/karin
Ветка: feature/v0.4-native-music-ui
Текущая база: актуальный HEAD PR #15
Не создавай новый PR.
Не делай merge.
Не удаляй ветки.
Работай в рамках существующего PR #15 и обновляй его.

В этой итерации нужен не новый большой концепт с нуля, а доведение текущего UI до более удачного, цельного и Cassette-like / Yandex Music-like состояния на основе уже реализованной версии.

Ориентиры:
1. Текущая реализованная версия PR #15.
2. Предыдущие требования по единой правой панели, Shuffle/Repeat, закреплённой панели и общей нативности.
3. Новый визуальный ориентир: Cassette-like style + композиционные решения Яндекс Музыки desktop.
4. Новый пользовательский скриншот-референс, приложенный в диалоге. Используй его как композиционный UX-ориентир, а не как объект буквального копирования.

Главная задача: сделать интерфейс более цельным, легче воспринимаемым и ближе к настоящему музыкальному приложению, сохранив уже реализованную функциональность.

==================================================
1. ОБЯЗАТЕЛЬНЫЕ ИЗМЕНЕНИЯ UI/UX
==================================================

1.1. Player Bar по умолчанию скрыт
---------------------------------
Сейчас нижний плеер постоянно виден. Это нужно изменить.

Требование:
- Пока ничего не воспроизводится, нижний Player Bar скрыт.
- После запуска трека Player Bar должен плавно появляться снизу.
- При полной остановке воспроизведения / отсутствии активного трека Player Bar может снова скрываться.
- Анимация появления должна быть аккуратной, нативной, без резких скачков.
- При pause Player Bar не исчезает.
- Если сохранено текущее состояние воспроизведения и трек активен при старте приложения, Player Bar может сразу появляться в соответствующем состоянии.

Не ломай существующую playback-логику, GStreamer, MPRIS и PlaybackController.
Visible Stop button по-прежнему не нужен.

1.2. Правая панель — визуально ближе к референсу
------------------------------------------------
Сейчас правую панель нужно приблизить по стилю и композиции к приложенному примеру.

Сохрани архитектурный принцип:
- одна универсальная правая панель;
- она остаётся закреплённой;
- не закрывается по внешнему клику;
- умеет показывать минимум Track Info и Queue;
- смена трека обновляет содержимое без закрытия.

Но переработай её UI:
- более цельная композиция;
- шапка/верх панели более аккуратная;
- обложка и метаданные должны выглядеть как единый музыкальный блок;
- в режиме Track Info панель должна ощущаться как полноценный музыкальный side panel, а не как технический контейнер;
- панель должна открываться визуально цельно, как одна поверхность;
- внутренняя визуальная иерархия должна быть ближе к референсу.

Дополнительно:
- правая панель должна открываться по нажатию не только на маленькую обложку в плеере;
- она должна открываться по нажатию на весь блок текущего трека в Player Bar (обложка + название + исполнитель + область метаданных как единая clickable zone);
- при этом отдельные действия внутри этого блока не должны ломать доступность и фокус.

1.3. Like / Dislike в Player Bar
--------------------------------
Добавь в нижний плеер кнопки:
- "нравится";
- "не нравится".

Требования:
- если API Яндекс Музыки/текущие реальные контракты подтверждают поддержку этих действий — реализуй настоящую интеграцию;
- если dislike не подтверждён или не поддерживается надёжно текущими реальными контрактами, не имитируй работающую функциональность;
- в таком случае честно зафиксируй ограничение и выбери корректный UX-вариант:
  либо скрыть неподдерживаемое действие,
  либо явно сделать его недоступным/неактивным в dev-документации и acceptance notes.
- Like не должен быть декоративной кнопкой.
- Не выдумывай API.

Нужно сохранить инженерную честность:
никакой фальшивой "дизайнерской" поддержки неподтверждённой функции.

1.4. Primary navigation упростить и сделать более Cassette-like
---------------------------------------------------------------
Текущую структуру primary destinations нужно упростить.

Хочу видеть упрощённую навигацию по аналогии с Cassette / ближе к примеру:
- вкладка/сегмент "Моя волна" — пока заглушка;
- вкладка/сегмент "Нравится";
- вкладка/сегмент "Плейлисты".

Требования:
- навигация должна быть простой, очевидной и визуально лёгкой;
- без выпадающих списков как основного паттерна переключения разделов;
- вкладки/сегменты должны быть проще и чище текущих dropdown-переключателей;
- стиль должен быть Cassette-like: нативно, компактно, минималистично, понятно;
- search остаётся доступным, но не должен снова превращать интерфейс в набор разрозненных технических контролов.

Смысл вкладок:
- "Моя волна" — пока нерабочая продуктовая заглушка, но аккуратно оформленная;
- "Нравится" — единое место для понравившихся треков и релевантных liked entities;
- "Плейлисты" — пользовательские и понравившиеся плейлисты, без идиотских выпадающих списков и лишних промежуточных состояний.

Если нужно, отдели "liked tracks" и "liked playlists" визуальными секциями внутри страницы, а не dropdown-переключателями.

1.5. Убрать пагинацию треков
----------------------------
Треки не должны показываться кусками через грубую видимую пагинацию.

Нужно:
- убрать явную пагинацию треков;
- реализовать непрерывную подгрузку / continuous loading при скролле;
- список должен ощущаться непрерывным;
- пользователь не должен вручную переключать страницы треков;
- при этом не ломай производительность и не загружай бесконтрольно всё сразу.

Нужен внятный lazy loading / infinite scroll подход:
- запрашивай данные порциями;
- подгружай заранее или по достижению нижнего порога;
- показывай корректное loading state;
- обрабатывай конец списка;
- сохраняй устойчивость при сетевых ошибках и повторных запросах;
- не дублируй элементы;
- не теряй позицию прокрутки.

Это касается списков, где раньше использовалась пагинация треков.

2. КОМПОЗИЦИОННЫЕ И ВИЗУАЛЬНЫЕ ПРАВКИ
==================================================

Нужен заметный, но не радикально новый визуальный refinement текущего результата.

Требуется:
- усилить Cassette-like характер интерфейса;
- сделать UI чуть более спокойным, стильным и лёгким;
- сделать музыкальные обложки более центральным элементом;
- упростить лишние визуальные конструкции;
- убрать ощущение “GTK-прототипа”.

Обязательно:
- минимум лишнего текста;
- визуальная интуитивность важнее служебных подписей;
- единая система отступов, плотности и размеров;
- аккуратные сегменты/tabs;
- более приятный Header area;
- улучшить композицию контента и плеера, чтобы всё ощущалось частью одного приложения.

Не нужно:
- перегружать интерфейс;
- делать glassmorphism;
- добавлять шумные градиенты;
- превращать всё в копию Яндекс Музыки;
- буквально копировать Cassette.

Нужно:
- взять лучшие UX-решения;
- сохранить нативность GTK4/Libadwaita;
- сделать Karin самостоятельным приложением.

==================================================
3. ПРАВАЯ ПАНЕЛЬ И ОЧЕРЕДЬ
==================================================

Существующий принцип единой панели правильный — сохраняем.

Нужно:
- сохранить одну правую панель для Track Info / Queue;
- не возвращать отдельную основную страницу Queue;
- переключение Track Info ↔ Queue должно оставаться в пределах одной панели;
- панель должна оставаться открытой при навигации, скролле, смене трека и ресайзе;
- вся поверхность панели продолжает двигаться как единый слой при открытии/закрытии.

Дополнительно:
- в режиме Track Info панель визуально ближе к музыкальному info sidebar;
- в режиме Queue панель тоже должна быть более удобной и визуально цельной;
- структура Queue должна быть более музыкально-ориентированной, а не как техсписок;
- если уместно, улучши визуальное разделение current / next / history;
- если на основе референса уместно добавить небольшой related section или вторичный контекст в Track Info — делай только если это реально опирается на уже имеющиеся данные и не требует выдуманного API.

Не придумывай неподтверждённые рекомендации, “Мою волну” или похожий динамический контент, если нет подтверждённой функциональной базы.

4. ЛОГИКА И ОГРАНИЧЕНИЯ
==================================================

Сохрани и не сломай:
- авторизацию;
- persistent sign-in;
- MusicService;
- StreamResolver;
- GStreamer playback;
- PlaybackContext;
- текущую очередь;
- Shuffle;
- Repeat Off / Queue / One;
- MPRIS и его текущую синхронизацию;
- кеш;
- server-confirmed playlist creation;
- общую архитектурную разделённость.

Не добавляй:
- Electron;
- web wrapper;
- отдельный браузерный UI;
- второй аудиодвижок;
- фоновые демоны;
- фейковые данные в production UI.

Like/dislike, Wave placeholder и похожие элементы должны быть реализованы инженерно честно.

Agent A — UX / Visual refinement

- сопоставляет с новым референсом;

- делает скрытый по умолчанию Player Bar;
- анимацию появления снизу;
- открытие правой панели по клику на весь current-track block;
- интеграцию like/dislike controls в footer;
- refinement правой панели под референс.

Agent D — Playback / integration safety
- следит, чтобы не сломались PlaybackController, queue, MPRIS, Shuffle/Repeat;
- проверяет like/dislike integration against real contracts;
- не допускает фейковой функциональности;

Agent E — QA / acceptance
- проверяет UI на реальных GTK screenshots;
- проверяет wide / medium / compact;
- проверяет appearance/disappearance Player Bar;
- проверяет right panel behavior;
- проверяет infinite scrolling;
- проверяет keyboard/mouse interactions;
- проверяет CI и регрессию.

Если суб-агенты недоступны, выполни те же роли последовательно, но не сокращай объём задачи.
