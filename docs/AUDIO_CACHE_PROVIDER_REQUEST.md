# Запрос провайдеру: хранение и повторное использование аудио Karin

Исторический неотправленный запрос от 2026-11-06. Его прежнее условие
отключения всех сервисных записей заменено локальной HTTP-политикой в PR #26;
вопросы применимых прав и публичного распространения остаются отдельными.

Подготовлено 2026-11-06. **Не отправлено.** Адресат — поддержка/партнёрская
команда Яндекс Музыки через официальный канал, указанный в
[условиях сервиса, п. 2.12](https://yandex.ru/legal/music_termsofuse/ru/).
Ответ должен относиться к Karin; сведения о возможностях других приложений
не заменяют разрешения. Контекст исследования: [AUDIO_CACHE_REVIEW](AUDIO_CACHE_REVIEW.md).

**Тема:** Условия разрешённого локального кеширования в независимом Linux-клиенте Karin

Karin — независимый открытый Linux-клиент на Rust/GTK/GStreamer. Просим уточнить
разрешённый способ прозрачного локального кеширования прослушиваемых треков.
Планируется только личное использование внутри приложения: приватное хранилище,
общая квота и LRU, отсутствие экспорта и массовых загрузок, удаление при выходе
из аккаунта и проверка текущего доступа онлайн перед каждым повторным
использованием. Offline Mode в этот запрос не входит. Работающий вход/поток
и подписка сами по себе не трактуются нами как разрешение на сохранение.

Просим подтвердить:

1. Допускается ли Karin сохранять полный уже разрешённый аудиоресурс и повторно
   использовать его после онлайн-проверки? Какой договор/разрешение и какая
   клиентская регистрация применимы к этому сценарию и публичному распространению?
2. Какой официальный API/контракт допускает получение ресурса для такого хранения,
   для каких форматов, территорий, подписок и типов музыкальных материалов?
   Нужны ли отдельные scopes, права либо партнёрское соглашение?
3. Какой endpoint и конкретные поля/значения подтверждают **текущий доступ именно
   к сохранённой версии ресурса**? Достаточна ли новая выдача того же ресурса или
   требуется отдельная проверка? Как связать ответ с аккаунтом, треком, форматом
   и версией без сохранения подписанного URL или OAuth-токена в кеше?
4. Что означают `GET /account/status` → `permissions.until`, `values`, `default`
   и `cacheLimit` для независимого клиента? Какие из них действительно разрешают
   хранение/повторное использование, а какие описывают другие возможности?
5. Каковы обязательные ограничения хранения: срок, число копий/устройств, формат
   защиты, изменение версии ресурса, отзыв прав, блокировка трека, изменение
   подписки/аккаунта? Какие ответы требуют немедленного удаления, а какие только
   запрета повторного воспроизведения? Сетевой сбой не должен подменять допуск.
6. Какие правила очистки и проверки следует применять после перезапуска, logout
   и отзыва разрешения? Нужны ли обязательные события использования сохранённых
   байтов и как отправлять их без повторения неопределённого запроса?

Просим предоставить применимое разрешение и проверяемую спецификацию с
положительными/отрицательными примерами **обезличенных** ответов. Ответ вида
«кеш поддерживается приложением Яндекса» либо один `cacheLimit` не определяет
контракт для Karin. Токены, cookies, персональные ответы, музыкальные файлы
и подписанные адреса передавать для этого запроса не требуется.

До получения этих данных Karin оставляет сервисное сохранение/повторное
использование выключенным. Инфраструктура общего кеша и его проверка не
объявляются подтверждением права на хранение музыкального каталога.
